# 医患问诊沟通设计

## 目标

在不拉长患者“我的问诊”卡片的前提下，提供可展开的问诊详情与医患双向沟通。患者只能在医生已经接诊且问诊尚未完成时回复；医生只能处理分配给自己的问诊。

## 页面交互

### 患者端

- 问诊卡片默认只显示当前状态、最新一条医生回复摘要、沟通记录数量和“查看详细沟通”入口。
- 同一时间只展开一张问诊卡片，展开内容位于当前卡片内部，不跳转新页面。
- 展开区域分为“处理进度”和“医患沟通”两部分。
- “待接诊”仅显示等待提示；“接诊中”显示回复输入框；“已完成”只读。
- 发送成功后局部刷新当前问诊的沟通记录，不重新加载整页列表。

### 医生端

- 医生抽屉继续显示处理时间线。
- 新增独立的“医患沟通”区域，展示患者和医生消息。
- 普通回复通过消息接口发送；开始接诊和完成问诊仍通过现有状态接口。
- 完成问诊时填写的最终回复同时进入处理记录和沟通记录。

## 数据模型

新增 `consultation_messages` 表：

- `id`
- `consultation_id`
- `sender_type`：`patient` 或 `doctor`
- `sender_id`：患者档案 ID 或医生用户 ID
- `sender_name`：发送者名称快照
- `content`
- `created_at`

问诊处理状态继续保存在 `consultation_progress_records`。沟通消息不承担状态流转职责。

迁移脚本会把历史处理记录中非空的 `doctor_note` 回填为医生消息，避免历史回复在新界面消失。

## 接口

患者端：

- `GET /api/patient/consultation/{id}/messages`
- `POST /api/patient/consultation/{id}/messages`

医生端：

- `GET /api/doctor/consultations/{id}/messages`
- `POST /api/doctor/consultations/{id}/messages`

列表接口增加轻量摘要字段：

- `messageCount`
- `latestMessage`
- `latestMessageSenderType`
- `latestMessageAt`

完整消息只在用户展开问诊或医生打开处理抽屉时加载。

## 权限与校验

- 患者只能访问 `patient_account_id` 属于自己的问诊。
- 医生只能访问 `doctor_id` 属于自己的问诊。
- 双方仅可在“接诊中”发送消息。
- 待接诊和已完成问诊拒绝新增消息。
- 消息去除首尾空白后不能为空，最大长度 2000 字。
- 管理员本阶段不参与沟通，也不新增代发功能。

## 兼容性

- 保留 `consultations.doctor_note` 和 `consultation_progress_records.doctor_note`。
- 医生完成问诊的最终回复继续写入处理记录，同时新增沟通消息。
- 历史医生回复由迁移脚本回填，前端不拼接两套数据，避免重复展示。

## 错误与状态

- 首次展开显示局部加载状态。
- 加载失败保留卡片并提供重新加载入口。
- 发送期间禁用输入和发送按钮，避免重复提交。
- 权限、状态变化或登录过期以服务端结果为准，并显示明确中文提示。

## 不包含

- WebSocket 或实时推送
- 已读未读状态
- 图片、文件或语音附件
- 消息撤回、编辑和删除
- 已完成问诊重新开启

## 验收

1. 医生开始接诊并发送回复。
2. 患者列表只显示摘要，展开后看到完整回复。
3. 患者发送补充信息，医生端可以读取并继续回复。
4. 医生完成问诊，患者仍可查看历史，但不能继续发送。
5. 其他患者、其他医生、未登录用户均不能访问该问诊消息。
6. 空消息、超长消息和错误状态发送均被拒绝。
